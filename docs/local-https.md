# Local domains and HTTPS

ArcBox gives Docker containers local DNS names and routes their web services through ports 80 and 443. The daemon keeps the root private key in the user's macOS Keychain. The guest keeps leaf private keys and requests signatures from the daemon. The privileged helper handles public certificates only.

## User operations

Containers and HTTP services can run without local CA trust. Enable local HTTPS from Desktop settings or run `abctl tls trust` in the login session. macOS controls authorization for changes to system trust. Existing correct trust does not require another authorization.

Run `abctl tls status --json` to inspect the current root's fingerprint, validity, publication, and trust. Run `abctl tls untrust` to remove system trust without stopping containers. Trust status does not prove that DNS, a route, or an upstream service works.

The `certificate_state` field distinguishes `missing`, `valid`, `renewal_due`, `expired`, and `not_yet_valid` independently of trust. Renewal is due when a valid root expires within 30 days. A root in that renewal window can remain trusted. Check the Mac's date and time when a certificate is not yet valid. Desktop does not request trust authorization for a missing or inactive certificate. Browser observation also requires a valid certificate; restoring validity starts a new observation cycle for the same root.

Run `abctl tls repair` to restore a missing or damaged `tls/ca.pem` from the profile's existing Keychain CA. Repair does not create a key or change trust. The optional `--expected-fingerprint` pins the current root. Repair rejects an inactive root, multiple matching Keychain items, and a publication containing a recoverable different certificate or multiple PEM objects. A repaired file does not establish that trust in an unknown previous root was removed.

Run `abctl tls rotate` to replace the root while the daemon is running, including in `--no-linux-vm` mode. The daemon creates the replacement private key. The login-session CLI authorizes the replacement, verifies native trust, and revokes the exact previous root. The daemon then publishes the replacement, switches its signer, and deletes the retired identity. The optional `--expected-fingerprint` pins the current root before authorization. Repeated preparation reuses the pending candidate. Desktop exposes the same operation as **Settings → System → Local HTTPS → Renew Certificate** for valid or expired roots, including interrupted rotation retries.

Canceling replacement authorization preserves the previous publication. If an interruption occurs after revocation, HTTPS can remain unavailable until `abctl tls rotate` completes the pending operation. The journal retains both public certificates for recovery. Rotation does not update the trust stores of already-running containers; their client trust requires a separate refresh.

Trust, repair, rotation, and revocation are exclusive per profile through native authorization. A concurrent command fails until the active command completes or the user cancels authorization. Status remains read-only and does not take that lock.

The [authorization decision](adr/0007-local-https-independent-of-startup.md) separates HTTPS from Docker readiness. The [installed validation log](logs/2026-10-08-helper-ca-trust.md#installed-desktop-authorization-and-restart) covers the earlier startup-authorization flow. That evidence does not validate the new on-demand flow.

## Service discovery contract

The daemon's `--dns-domain` option takes precedence over `ARCBOX_DNS_DOMAIN`; the default is `arcbox.local`. Host DNS receives the validated suffix before VM startup. The System VM receives the same suffix through `arcbox.dns_domain=` on the kernel command line. DNS replies, HTTP Host and TLS SNI probes, service URLs, and HTTPS ownership checks use that suffix. A changed suffix participates in the existing VM boot-configuration drift check.

The guest reports typed installed routes through `ListGuestWebServices`. The snapshot includes only names that resolve to the selected container address. The host validates route identities, addresses, names, and ports, then checks every name against its current Registry owner and address. Stale and conflicting names disappear from `SystemService.ListWebServices` and `WatchWebServices`. A managed backend produces separate directory entries for `.local` aliases with HTTPS and other aliases with HTTP only. Native TLS retains all currently owned aliases.

Both List RPCs accept a concrete `hostname`; an empty value lists exact aliases. A concrete lookup resolves current ownership, including wildcard claims, and returns at most one installed service with a matching owner and address. Desktop queries this endpoint before opening and after authorization, including browser-observed names absent from its cached directory. Reconnects invalidate pending results. The paired source and focused tests pass; installed browser acceptance remains pending. An unavailable container exact claim outside a reserved resource tree can still permit a broader wildcard to match.

Host DNS and both VMM datapaths share the live Registry and the configured suffix for exact relative aliases. Wildcard resolution uses the Registry directly. Concrete mDNS projections cannot override conflicts, reservations, or delegated names. This source wiring still requires installed VM validation.

Host and guest use one constructor to reserve `host`, `host.<configured suffix>`, `host.docker.internal`, `gateway.docker.internal`, and the configured index apex before resource registration. Exact reservations persist when their address is unavailable; containers cannot claim these names through exact or wildcard aliases. The guest forwards these exact builtin names to its existing gateway for the host's answer. Descendants remain separate names.

Machines use `<name>.machine.<suffix>` and sandboxes use `<id>.sandbox.<suffix>`. These resource trees stay reserved after address loss or resource removal. Container aliases cannot enter either tree. The guest forwards machine queries to the host; sandbox queries remain inside the sandbox reservation. Flat and bare resource aliases are removed.

The shared Registry selects the longest instance root before resource claims. Unavailable roots terminate lookup; effective authority changes invalidate asynchronous DNS/TLS revisions. Host and VMM DNS forward other-instance queries only to the explicit loopback endpoint, without ordinary cache or public-upstream fallback, and recheck authority before returning the response. The daemon projects helper authority snapshots into this Registry and delivers complete snapshots to the captured physical System VM through one retained connection. Only authority revisions trigger replacements; resource-only changes do not. The host checks physical identity after Open and each acknowledgment, monitors idle EOF and VM identity, and joins transport workers before reconnecting. Profiles without host DNS ownership deliver an empty snapshot without activating the helper.

The guest applies complete snapshots before acknowledgment and synchronously withdraws known roots when the connection ends. Later source revisions invalidate pinned routes even when the roots are unchanged. Source socket tests cover both host transports, cancellation, physical VM replacement, idle EOF, and complete replay. Installed multi-instance DNS and browser acceptance remain pending.

The NetworkManager Registry watch reports effective ownership changes even when wildcards, unavailable resources, or custom suffixes produce no mDNS record. Resolver lease reconciliation subscribes before reading the complete Registry snapshot and publishes configured and custom `.local` roots, including unavailable and conflicting claims.

The helper provides connection-bound resolver leases with verified daemon identity, exclusive exact roots, complete-set publication, and exact-content cleanup. Startup recovery removes only recognized orphan lease files. A bounded authority watch reports complete connection-relative roots, active ports, accepted revisions, and retained unavailable roots. Transport EOF retires authority and cancels watches before request drain and file cleanup. Failed cleanup retains ownership until helper restart. The daemon owns the lease/watch transport and mDNS future; it withdraws authority and joins the mirror before closing that transport. Bonjour publishes only granted concrete `.local` records, including custom roots and apexes, and resyncs the latest snapshot after notifications. Thirteen resolver tests cover snapshot confirmation, real Unix-socket cancellation, EOF, watch updates, physical VM changes, cleanup ordering, error retention, and complete replay after reconnection. Installed cutover remains pending.

Guest reconnects validate the complete container list and every inspect response before changing DNS. Snapshot and event updates wait for the route task to invalidate previous service publications before replacing ownership. Failed rule cleanup retains an unavailable owner for retry. This ordering protects managed HTTPS publication; kernel NAT rules and DNS do not change atomically. Twelve event tests and two route tests cover these transitions, including a late scan and unchanged-address namespace replacement. Installed guest NAT validation remains pending.

Domain actor shutdown withdraws installed service entries and index ownership before cancelling the frontend. It joins every frontend task before sweeping domain and index redirects, awaits both cleanups, and reports all failures. Task abort also invalidates installed entries and pinned TLS routes; the next agent startup sweeps remaining redirects. Docker retains ownership of container DNS registrations. Kernel cleanup remains unverified.

Host rename and network refresh replace Registry ownership without first deregistering the container. An unchanged refresh preserves the signing revision, and a rename removes the old display alias. Start, restart, stop, kill, remove, and rename share Runtime's lock for the full container ID through the guest mutation and host publication. Each request resolves its token before acquiring the lock and preserves the original query when forwarding the canonical ID. Network connect and disconnect hold the same lock and replace only the request's `Container` field. A forced disconnect after an explicit container 404 can remove an orphan endpoint without changing host ownership. Cold recovery and periodic reconciliation capture an idle host generation and physical VM before querying every running container. They reject stale snapshots and publish Registry ownership and aliases together after port work. An ordinary bind failure preserves untouched healthy listeners; successful earlier listener work may remain.

Host port refresh preserves equivalent healthy listeners and removes listeners when bindings become empty. Equality includes the effective host address, host port, guest port, protocol, and machine. Canceled or exited listeners complete cleanup before recovery. Host socket tests cover refresh, conflicting destinations, TCP/UDP sharing, and cancellation; installed forwarding validation remains pending.

Each macOS machine retains its current listener manager and any manager awaiting retirement in Runtime. Adoption takes the VMM's next manager only after acquiring the rules and listener locks and completing prior retirement. Engine tags each physical start or reboot with a `VmIncarnation`; manager transfer validates that expected live incarnation under the VM lock, and cached listener reuse requires the same tag. Cancellation preserves cleanup ownership during replacement, System VM retirement, and shutdown. Docker lifecycle admission captures the ready physical VM before inspect and validates it after taking the canonical container lock. Its activity lease ends synchronously on cancellation, without holding the global commit lock through guest I/O. Request-driven and snapshot publication share the global commit lock, pin port cleanup to the expected VM, and publish aliases/DNS under the final synchronous Engine guard. Shared DNS and port writers invalidate earlier snapshots; DNS registration propagates closed-admission errors. Publication from a replacement VM first retires the previous VM's container state. The reconciler also checks physical identity on every notification and timer tick. A 30-second whole-query deadline prevents unanswered guest requests from blocking those checks indefinitely. Graceful and forced Runtime shutdown close admission before storage cleanup, then clear host network state under the existing locks. Late snapshots and shared writers cannot republish after cleanup.

Serial Runtime validation passed 83 tests, followed by one additional canceled-retirement socket regression. Coverage includes manager cancellation, stale snapshots, healthy listeners, shared-writer admission, physical VM replacement, and shutdown closure. Eleven reconciler tests cover coalesced notifications, unannounced physical changes, whole-query deadlines, and stopped-VM checks. Strict all-target Core/Docker Clippy and scoped formatting pass; computer/API/daemon gates passed in the preceding shared-writer slice. Two earlier parallel runs exposed bind and post-teardown connection failures; the isolated teardown regression passes. Parallel socket behavior remains under investigation, so these results do not establish concurrent socket-test stability.

For a container attached to multiple networks, host DNS, guest DNS, service discovery, and published-port mirrors select the first valid IPv4 address in network-name order. They ignore the deprecated top-level `NetworkSettings.IPAddress`. Domain NAT retains all distinct container IPv4 addresses.

Clients use the supplied URLs. Upstream port fields describe the application listener, not the public URL port. A managed HTTPS endpoint requires ArcBox CA trust. A passthrough endpoint uses the application's own TLS and must not request ArcBox CA authorization. A directory error ends the stream; clients must clear stale entries.

Managed HTTPS checks the actual requested name against current ownership and the `.local` CA namespace before observation or certificate generation. A custom `.local` alias can use the guest proxy even when the configured suffix is `containers.test`. Other names support HTTP and native TLS. New roots permit concrete names under `.local`; existing roots retain their actual scope until explicit rotation. Independent custom aliases participate in resolver leases and Bonjour projection; native macOS resolution still requires installed validation.

The [CA scope decision](adr/0008-local-ca-covers-local-domains.md) preserves the public-DNS and IP restrictions. The broader scope includes other LAN `.local` services, so a compromised root key has authority beyond ArcBox's own namespace. Ordinary signing still requires current host ownership. The broader certificate constraint does not grant resolver ownership over all `.local`.

The daemon pins each signing connection to a captured machine name and physical VM run. The native connection holds the Engine VM-entry guard. The signer checks that guest’s current DNS authority before signing and certificate delivery. System guests retain container and built-in index scope. Machine authority permits only the exact canonical machine name at its current bridge address while Running. System and machine signing workers run independently, including in `--no-linux-vm` mode. Lifecycle events and periodic rescans cancel retired sessions. Each machine host hold remains active until native connection and signing work finish. Unavailable signing listeners retry after one second. Shutdown cancels socket waits and joins every worker before stopping Runtime.

The host verifies each CSR's signature and single DNS name before signing. The name must belong to the captured guest’s current container, built-in index, or canonical machine authority and resolve to that authority’s address. Index authorization requires one exact apex claim, the configured gateway, and current instance authority. The host rechecks the registration after signing, so deletion, ownership transfer, or registration replacement discards an in-flight result. The guest pins the selected owner, registration revision, and installed route identity at the connection's original destination. The guest rechecks that route after authorization, certificate configuration, TLS handshake, and upstream connection before forwarding application bytes. Failed connections atomically invalidate only their pinned route; an old failure cannot withdraw its replacement.

Managed HTTPS negotiates HTTP/2 or HTTP/1.1 with ALPN and forwards either protocol to a verified cleartext backend. Discovery prefers HTTP/2 on an independent bounded socket before probing HTTP/1.1. An explicit HTTP port remains published when probes fail, but application forwarding requires a verified protocol. Application requests are never replayed for protocol discovery.

The relay replaces `X-Forwarded-Proto` with `https` and preserves authority, path/query, Location, and repeated Set-Cookie values. Bodies remain streaming. With HTTP/2 on both sides, native gRPC preserves unary and streaming calls, status, binary metadata, trailers, and compressed message bytes. Streams share the HTTP/2 upstream connection. Cancellation remains observable after response completion while a request upload is active. HTTP/2 streams use independent HTTP/1 upstream connections when required. Each additional connection rechecks the original route before and after connecting. HTTP/1 WebSocket upgrades preserve buffered frames, including on a backend that also supports HTTP/2. Listener shutdown joins all internal tasks. Native TLS passes through unchanged.

When converting an HTTP/2 body to HTTP/1.1, the relay uses chunked framing and requires trailer names in the initial `Trailer` header. HTTP/1.1 clients must send `TE: trailers` to receive response trailers. Declared, supported trailer fields retain repeated values. Undeclared, forbidden, or unaccepted trailers fail the HTTP/1.1 message. Arbitrary HTTP/2 trailer sets are not supported across the HTTP/1.1 boundary.

## Browser index

The configured apex serves an index on ports 80 and 443. Managed HTTPS requires a `.local` apex and the trusted ArcBox CA. The HTTPS index supports HTTP/2 and HTTP/1.1. Every request must match the current apex and port through its authority or Host field. The guest binds the shared frontend before installing exact gateway redirects. Both redirects must precede Docker's PREROUTING jump before the guest publishes `system:index`. The host publishes that endpoint only after validating the guest response for the current physical VM.

Failed guest publication withdraws the index and retries after one second, even without containers. Shutdown withdraws the registration before canceling and joining the frontend, then sweeps only `arcbox-index:` redirects. The page uses current service URLs and distinguishes unavailable Docker discovery from an empty list. Kernel NAT and installed browser validation remain pending.

## System VM client trust

The daemon delivers its current public root to the System VM's system CA bundle once the agent is ready. It repeats delivery after a VM replacement or published-root change. CA preparation failures preserve the installed root. Unrelated roots and user additions remain intact. Already-running containers require separate trust updates. Installed VM HTTPS validation remains pending.

## Machine web configuration

Run `abctl machine web NAME` to read the saved HTTP and HTTPS backend policies. Set `--http-port` or `--https-port` to `auto`, `off`, or a port from 1 through 65535. Omitted options preserve the current value. Both protocols default to `auto`; an explicit HTTPS port selects native TLS. Inspect, clone, and archive transfer retain these settings. This command saves configuration only; guest routing and installed machine HTTPS remain pending.

## Machine client trust

The machine agent accepts authenticated public-root snapshots on Debian, Ubuntu, and Alpine. It updates only `/usr/local/share/ca-certificates/arcbox-local-ca.crt`, invokes the installed `update-ca-certificates`, and verifies and syncs the rebuilt system PEM bundle before acknowledging installation or explicit removal. Updater failure leaves reconciliation pending until replay. Missing tools or stores and other distributions return an error.

The distro updater preserves other source anchors and may replace direct edits to its generated bundle. The daemon automatically delivers its current public root to running machines, including when the System VM is disabled. Each machine reconciles independently after startup, root replacement, and physical VM replacement. Stopping or removing a machine cancels delivery and waits for its connection and request before releasing the host hold. Failed CA preparation preserves installed trust. Machine web routes remain pending. Debian and Alpine updater behavior has isolated container evidence; Ubuntu and installed machine client trust remain unverified.

## Container client trust

The Docker API proxy injects the current public CA into supported regular PEM system bundles before container start. Set `dev.arcbox.add-ca-certificates=false` to disable injection. Injection preserves unrelated roots and does not execute image code. The host checks the published certificate against the active Keychain identity.

Injection skips running containers, read-only roots, caller-mounted bundles, symbolic bundle paths, and containers with custom certificate environment variables. A restart of a running container does not refresh trust. Java keystores and Node's bundled roots are not managed; runtimes configured to use the system bundle can use the injected root. Image builds and Docker requests made directly inside the VM bypass this hook. A package manager that rebuilds the bundle can remove the injected root.

The opt-in real Docker regression verifies default curl trust, opt-out, repeat injection, and preservation of unrelated roots. [Rerun instructions and scope](logs/2026-10-08-custom-local-domains.md#verify-container-client-trust-with-real-docker) distinguish this test from installed ArcBox validation.
