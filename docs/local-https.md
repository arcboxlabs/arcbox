# Local domains and HTTPS

ArcBox gives Docker containers local DNS names and routes their web services through ports 80 and 443. The daemon keeps the root private key in the user's macOS Keychain. The guest keeps leaf private keys and requests signatures from the daemon. The privileged helper handles public certificates only.

## User operations

Containers and HTTP services can run without local CA trust. Enable local HTTPS from Desktop settings or run `abctl tls trust` in the login session. macOS controls authorization for changes to system trust. Existing correct trust does not require another authorization.

Run `abctl tls status --json` to inspect the current root's fingerprint, validity, publication, and trust. Run `abctl tls untrust` to remove system trust without stopping containers. Trust status does not prove that DNS, a route, or an upstream service works.

The `certificate_state` field distinguishes `missing`, `valid`, `renewal_due`, `expired`, and `not_yet_valid` independently of trust. Renewal is due when a valid root expires within 30 days. A root in that renewal window can remain trusted. Check the Mac's date and time when a certificate is not yet valid. Desktop does not request trust authorization for a missing or inactive certificate. Browser observation also requires a valid certificate; restoring validity starts a new observation cycle for the same root.

Run `abctl tls repair` to restore a missing or damaged `tls/ca.pem` from the profile's existing Keychain CA. Repair does not create a key or change trust. The optional `--expected-fingerprint` pins the current root. Repair rejects an inactive root, multiple matching Keychain items, and a publication containing a recoverable different certificate or multiple PEM objects. A repaired file does not establish that trust in an unknown previous root was removed.

Run `abctl tls rotate` to replace the root while the daemon is running, including in `--no-linux-vm` mode. The daemon creates the replacement private key. The login-session CLI authorizes the replacement, verifies native trust, and revokes the exact previous root. The daemon then publishes the replacement, switches its signer, and deletes the retired identity. The optional `--expected-fingerprint` pins the current root before authorization. Repeated preparation reuses the pending candidate. Desktop exposes the same operation as **Settings → System → Local HTTPS → Renew Certificate** for valid or expired roots, including interrupted rotation retries.

Canceling replacement authorization preserves the previous publication. If an interruption occurs after revocation, HTTPS can remain unavailable until `abctl tls rotate` completes the pending operation. The journal retains both public certificates for recovery. Rotation does not update the trust stores of already-running containers; their client trust requires a separate refresh.

Trust, repair, rotation, and revocation are exclusive per profile through native authorization. A concurrent command fails until the active command completes or the user cancels authorization. Status remains read-only and does not take that lock.

The [authorization decision](adr/0007-local-https-independent-of-startup.md) separates HTTPS from Docker readiness. The [installed validation log](logs/2026-10-08-helper-ca-trust.md#installed-desktop-authorization-and-restart) covers the earlier startup-authorization flow. That evidence does not validate the new on-demand flow.

## Service discovery contract

The daemon's `--dns-domain` option takes precedence over `ARCBOX_DNS_DOMAIN`; the default is `arcbox.local`. Host DNS receives the validated suffix before VM startup. The System VM receives the same suffix through `arcbox.dns_domain=` on the kernel command line. DNS replies, HTTP Host and TLS SNI probes, service URLs, and HTTPS ownership checks use that suffix. A changed suffix participates in the existing VM boot-configuration drift check.

The guest reports installed routes through `ListContainerWebServices`. The snapshot includes only names that resolve to the selected container address. The host validates route identities, addresses, names, and ports, then checks every name against its current Registry owner and address. Stale and conflicting names disappear from `SystemService.ListWebServices` and `WatchWebServices`. A managed backend produces separate directory entries for `.local` aliases with HTTPS and other aliases with HTTP only. Native TLS retains all currently owned aliases.

Both List RPCs accept a concrete `hostname`; an empty value lists exact aliases. A concrete lookup resolves current ownership, including wildcard claims, and returns at most one installed service with a matching owner and address. Desktop queries this endpoint before opening and after authorization, including browser-observed names absent from its cached directory. Reconnects invalidate pending results. The paired source and focused tests pass; installed browser acceptance remains pending. An unavailable exact claim without a resource boundary still permits a broader wildcard to match; resource-boundary retention remains unfinished.

Host DNS and both VMM datapaths share the live Registry and the configured suffix for exact relative aliases. Wildcard resolution uses the Registry directly. Concrete mDNS projections cannot override conflicts, reservations, or delegated names. This source wiring still requires installed VM validation.

Host and guest use one constructor to reserve `host`, `host.<configured suffix>`, `host.docker.internal`, `gateway.docker.internal`, and the configured index apex before resource registration. Exact reservations persist when their address is unavailable; containers cannot claim these names through exact or wildcard aliases. The guest forwards these exact builtin names to its existing gateway for the host's answer. Descendants remain separate names. Resource-owned boundaries, instance delegation, and resolver lease integration remain unfinished.

The NetworkManager Registry watch reports effective ownership changes even when wildcards, unavailable resources, or custom suffixes produce no mDNS record. Consumers subscribe before reading the complete Registry snapshot. Resolver lease reconciliation still needs to consume this feed.

The helper provides connection-bound resolver leases with verified daemon identity, exclusive exact roots, complete-set publication, and exact-content cleanup. Startup recovery removes only recognized orphan lease files. Temporary-directory and Unix-socket tests pass, including request failure, partial publication, and EOF cleanup. Failed cleanup retains ownership until helper restart. The daemon still uses its earlier resolver setup; authority watches, mDNS lifetime integration, and installed cutover remain pending.

Guest reconnects validate the complete container list and every inspect response before changing DNS. Snapshot and event updates wait for the route task to invalidate previous service publications before replacing ownership. Failed rule cleanup retains an unavailable owner for retry. This ordering protects managed HTTPS publication; kernel NAT rules and DNS do not change atomically. Twelve event tests and two route tests cover these transitions, including a late scan and unchanged-address namespace replacement. Installed guest NAT validation remains pending.

Host rename and network refresh replace Registry ownership without first deregistering the container. An unchanged refresh preserves the signing revision, and a rename removes the old display alias. Start, restart, stop, kill, remove, and rename share Runtime's lock for the full container ID through the guest mutation and host publication. Each request resolves its token before acquiring the lock and preserves the original query when forwarding the canonical ID. Network connect and disconnect hold the same lock and replace only the request's `Container` field. A forced disconnect after an explicit container 404 can remove an orphan endpoint without changing host ownership. The periodic reconciler still needs shared commit ordering and stale-snapshot fencing.

Host port refresh preserves equivalent healthy listeners and removes listeners when bindings become empty. Equality includes the effective host address, host port, guest port, protocol, and machine. Canceled or exited listeners complete cleanup before recovery. Host socket tests cover refresh, conflicting destinations, TCP/UDP sharing, and cancellation; installed forwarding validation remains pending.

Each macOS machine retains its current listener manager and any manager awaiting retirement in Runtime. Adoption takes the VMM's next manager only after acquiring the rules and listener locks and completing prior retirement. Engine tags each physical start or reboot with a `VmIncarnation`; manager transfer validates that expected live incarnation under the VM lock, and cached listener reuse requires the same tag. Cancellation preserves cleanup ownership during replacement, System VM retirement, and shutdown. Final liveness checks after asynchronous listener work and global host commit ordering remain pending.

The 74 Runtime tests pass with `--test-threads=1`, including deterministic manager-cancellation regressions and rejection of old cleanup after a replacement listener slot is installed. Strict all-target Engine/Core Clippy and scoped formatting pass. Two earlier parallel runs exposed bind and post-teardown connection failures; the isolated teardown regression passes. Parallel socket behavior remains under investigation, so the serial result does not establish concurrent socket-test stability.

For a container attached to multiple networks, host DNS, guest DNS, service discovery, and published-port mirrors select the first valid IPv4 address in network-name order. They ignore the deprecated top-level `NetworkSettings.IPAddress`. Domain NAT retains all distinct container IPv4 addresses.

Clients use the supplied URLs. Upstream port fields describe the application listener, not the public URL port. A managed HTTPS endpoint requires ArcBox CA trust. A passthrough endpoint uses the application's own TLS and must not request ArcBox CA authorization. A directory error ends the stream; clients must clear stale entries.

Managed HTTPS checks the actual requested name against current ownership and the `.local` CA namespace before observation or certificate generation. A custom `.local` alias can use the guest proxy even when the configured suffix is `containers.test`. Other names support HTTP and native TLS. New roots permit concrete names under `.local`; existing roots retain their actual scope until explicit rotation. macOS system resolution for independent custom aliases remains unfinished.

The [CA scope decision](adr/0008-local-ca-covers-local-domains.md) preserves the public-DNS and IP restrictions. The broader scope includes other LAN `.local` services, so a compromised root key has authority beyond ArcBox's own namespace. Ordinary signing still requires current host ownership. The broader certificate constraint does not grant resolver ownership over all `.local`.

The host verifies each CSR's signature and single DNS name before signing. The name must belong to a current host container DNS registration and resolve to that registration's address. The host rechecks the registration after signing, so deletion, ownership transfer, or registration replacement discards an in-flight result. The guest pins the selected owner, registration revision, and installed route identity at the connection's original destination. The guest rechecks that route after authorization, certificate configuration, TLS handshake, and upstream connection before forwarding application bytes. Failed connections atomically invalidate only their pinned route; an old failure cannot withdraw its replacement.

Managed HTTPS replaces `X-Forwarded-Proto` with `https` on every HTTP/1.1 request. The relay preserves Host, path/query, Location, and repeated Set-Cookie values. Bodies remain streaming; trailer capability is negotiated per hop. WebSocket upgrades preserve bytes already read with the handshake. Native TLS passes through unchanged. Managed HTTP/2 and gRPC translation are not implemented.

## OrbStack comparison sources

The comparison uses public product behavior. Do not infer undocumented implementation details or claim coverage for an unsupported protocol or trust store.

- [Container domains](https://docs.orbstack.dev/docker/domains): naming, custom domains, wildcards, index, and protocol discovery.
- [HTTPS](https://docs.orbstack.dev/features/https): first-use installation, container CA injection, private-key protection, and native HTTPS forwarding.
- [Forwarded scheme clarification](https://github.com/orbstack/orbstack/issues/1895#issuecomment-2803371612): OrbStack sets `X-Forwarded-Proto` for proxied HTTPS; direct HTTP does not receive that header.
- [Linux networking](https://docs.orbstack.dev/machines/network): machine names, port configuration, and macOS trust integration.
- [Kubernetes](https://docs.orbstack.dev/kubernetes/): Service addresses, `cluster.local`, and LoadBalancer/Ingress domains.
- [Menu bar](https://docs.orbstack.dev/menu-bar): service discovery and opening.
